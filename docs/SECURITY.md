# LabFlow security implementation baseline

Selected 21 October 2026 for authorized demo development. This records engineering choices; SRS approval/submission remain pending.

The browser and all request payloads are untrusted. MongoDB stores synthetic accounts, password hashes, sessions and lending state. Threats include role injection, cross-user access, forged browser mutations, credential guessing, session replay and conflicting inventory actions. Server validation/authorization and database constraints are authoritative.

- Passwords: 12–128 characters, at most 512 UTF-8 bytes; spaces/unicode allowed, no silent trimming/truncation. Node's asynchronous scrypt uses N=131072, r=8, p=1, 16 random salt bytes, 64 derived bytes and a 256 MiB maximum allocation. Compare equal-length derived values with timingSafeEqual. Missing-account login performs the same expensive verification against a dummy hash. Based on [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- Sessions: express-session with connect-mongo, no browser token storage, regeneration at login, explicit save before success, destruction at logout. Lifetime is eight hours absolute, enforced by the application independently of delayed TTL deletion. Production cookie is `__Host-labflow.sid`, HttpOnly, Secure, SameSite=Lax, path `/`, no Domain. Local HTTP uses `labflow.sid`. Login loads server-controlled user/role on protected requests. See [Express sessions](https://expressjs.com/en/resources/middleware/session/) and [connect-mongo](https://github.com/jdesboeufs/connect-mongo).
- CSRF: every mutation requires exact configured Origin, rejects cross-site Fetch Metadata, accepts JSON only and requires `X-LabFlow-Request: 1`. No CORS origins are enabled. HTML forms cannot set this header; cross-origin scripts require a preflight the API does not permit. Applies to login/registration too. See [OWASP custom-header guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
- Authentication limit: ten combined login/registration attempts per source IP per fixed 15-minute window, counted atomically in MongoDB across processes. Window identifiers use an HMAC rather than retaining raw IPs. Expired windows have a TTL index. Boundary responses use 429 and Retry-After. Fixed windows permit a burst across a window boundary; they do not claim sliding-window guarantees.
- Trust proxy stays disabled locally. Deployment must explicitly configure and verify the actual reverse-proxy topology before relying on client-IP limits or Secure cookies. Never trust arbitrary forwarded headers.
- Registration accepts name (2–120 trimmed characters), normalized valid email (maximum 254), and password only. Role/owner/state fields are rejected. User responses contain only id, name, email and role.
- Admin accounts are provisioned by an explicit local command that reads the password from an ignored environment file or runtime secret; it never prints it. Public APIs cannot create administrators. Existing accounts are never silently elevated.
- Errors expose stable codes and safe field hints, never stacks, MongoDB details, hashes or session values. Request bodies/credentials are never logged. Secrets require at least 32 random characters and live only in runtime configuration.
- Demo data only. Retention and real-student privacy policy remain unresolved; the app must not be represented as ready for real college use.

Quality baseline for implementation: auth/ownership/circulation target at least 80% line and branch coverage; lint/build/tests must pass, core screens remain keyboard accessible and usable at 320px. Coverage and automated accessibility evidence must be measured before claiming the targets pass.
