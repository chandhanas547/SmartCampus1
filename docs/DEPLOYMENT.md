## Free-tier tradeoffs and sources

Render Free services sleep after 15 idle minutes and can take about one minute to wake. The filesystem is ephemeral; all persistent accounts, sessions, auth limits and lending state belong in Atlas. Free services have no shell or one-off jobs. Use a dedicated free workspace without a payment method: quota exhaustion must suspend service/builds, not bill overages. If that condition cannot be met in the available account, stop before creating resources. Free rollback history is limited, so record the exact successful Git commit. See [Render Free limits](https://render.com/docs/free).

Atlas Free currently uses MongoDB 8.0 and three replicated nodes, with one Free cluster per project. This is a suitable candidate for the required transaction-capable topology, but real transactions/indexes/roles must still pass on the actual approved cluster. Do not assume local acceptance proves cloud behavior. See [Atlas Free limits](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/).

The Blueprint uses documented manual deployment, secret prompts and generated session-secret fields. Build installs development dependencies explicitly even with NODE_ENV=production, builds once, then prunes development dependencies. This exact shape was verified locally. See [Render Blueprint fields](https://render.com/docs/blueprint-spec).

## Runtime and access setup after approval

- Use a dedicated database `labflow` and database user `labflow_app` with readWrite only on that database, restricted to the approved cluster. Generate a unique random credential; store it directly in provider secrets. No URI/password in Git, logs or screenshots.
- Obtain the service's actual outbound CIDRs from Render's Connect → Outbound view and allow only those ranges in the new Atlas project. Ranges are shared with other regional Render services, so database authentication remains essential. Never substitute `0.0.0.0/0` for convenience. See [Render outbound IPs](https://render.com/docs/outbound-ip-addresses).
- Set APP_ORIGIN to the exact assigned HTTPS origin with no path/trailing slash; MONGODB_URI targets the dedicated database; SESSION_SECRET is generated by the host; HOST is 0.0.0.0; use the host's PORT. Node/npm are pinned. Do not upload `server/.env` or local seed credentials.
- Verify TLS termination and forwarded headers. The implementation supports zero/one trusted proxy hop; choose one only after confirming Render's actual topology and client-IP behavior. Tests prove forged forwarded HTTPS is ignored with proxy trust disabled, and secure host-only cookies work with the explicit simulated proxy. That is not verification of Render's deployment.
- Because Render Free has no shell/one-off jobs, provision one synthetic reviewer administrator from the local controlled command against the approved Atlas database. Temporarily allow only the operator's verified public `/32` address in the new Atlas project; remove that entry after provisioning/testing. Use an ignored secret file for that explicit command, not the local development seed. Delete the temporary plaintext provisioning secret afterward and deliver reviewer access privately through the owner's chosen channel. Do not put it in README/report/screenshots or send it to anyone without authorization.
- Local `seed:demo` deliberately refuses cloud databases. If published sample inventory is desired, add the six synthetic assets through the authenticated admin UI after approval. No real-person accounts or email sending.

## Monitoring and rollback

During live acceptance, inspect health, safe error counts, client errors, latency and provider memory. A readiness failure, broken authentication, allocation inconsistency or new repeated 500 response stops evaluation. Return to the last verified deployment commit through Render's manual deployment/rollback, then repeat health/session/core-flow checks. Keep Atlas data and indexes intact; code rollback does not mean database deletion or a destructive reset. No schema migration is currently planned. If no previous hosted version exists, suspend the demo and fix it rather than advertise success.
